# KV002: hardcoded credential

Severity: always an error.

## What it catches

A credential written into source, a notebook or a config file. kv-cli reports
a literal when either of these rules matches.

1. Its shape. A value pattern matches it under any name and anywhere in the
   file, including comments, notebook outputs and split strings such as
   `"ghp_abc" "def"`. The shapes cover AWS keys, GitHub, Slack, OpenAI,
   Anthropic, Stripe and Google keys, JWTs, PEM private keys and URLs with a
   password. [Detector set 2](#detector-sets) adds Azure Storage account
   keys, Databricks personal access tokens and SendGrid API keys.
2. Its name. It is assigned to, or compared with, a name that matches
   `secrets.key_patterns`, such as `*password*`, `*token*` or `*api_key*`.

```python
DB_PASSWORD = "s3cr3t-value-1234"         # KV002: name rule
if password == "s3cr3t-value-1234":       # KV002: comparison
```

The output redacts the value, shown as `value "s3…" (<redacted>, 17 chars)`,
so the CI log doesn't leak the credential.

## Detector sets

Built-in shapes ship in numbered sets, chosen with `secrets.detectors`. A set
never changes once released. New shapes arrive in a new set that you opt into,
so an upgrade can't change what an existing contract reports or what its
fingerprint pins.

| `secrets.detectors` | What is matched | When it applies |
| --- | --- | --- |
| `1` | `secrets.value_patterns` alone. By default that is 12 shapes: `aws_access_key_id`, `github_token`, `github_fine_grained_token`, `slack_token`, `anthropic_api_key`, `openai_api_key`, `openai_project_key`, `google_api_key`, `stripe_live_key`, `jwt`, `private_key_block` and `url_basic_auth`. | When the key is absent. Every contract written before 0.15.0 is on set 1. |
| `2` | Set 1, plus `azure_storage_key`, `databricks_pat` and `sendgrid_api_key`. | Since 0.15.0, when the contract says `detectors: 2`. `kv-cli init` writes it. |

What set 2 adds:

- **`azure_storage_key`**: an Azure Storage account key inside a connection
  string: `AccountName=…;AccountKey=`, then 88 base64 characters ending in
  `==` (a 512-bit key). A bare 88-character base64 string is not reported:
  hashes and digests have the same shape, and without the connection string
  the shape alone is no evidence of a key.
- **`databricks_pat`**: `dapi`, then 32 hex characters, with an optional
  `-<digits>` suffix. Under set 1 the Databricks profile already reports
  `dapi` and 32 lowercase hex characters in files that use Databricks. Set 2
  reports the token in every file, under any name, in either case.
- **`sendgrid_api_key`**: `SG.`, 22 characters, a dot, then 43 characters,
  each from `A-Z a-z 0-9 _ -`: 69 characters in all.

The examples the providers' own documentation prints are never reported
under set 2: the storage emulator's published key, and the token in
Databricks' examples, `dapi` followed by `12345678901234567890123456789012`.
Placeholders such as
`AccountKey=<account-key>` and `SG.xxxxxxxx.yyyyyyyy` don't have the shape.

To opt in, set the field in `.kovallent.yaml`:

```yaml
secrets:
  detectors: 2
```

The field is part of the contract, so setting it changes the fingerprint.
Update the pinned fingerprint in the same pull request; see
[Upgrading to 0.15.0](../configuration.md#upgrading). Any value other than
`1` or `2` is a contract error, reported on its line:

```
.kovallent.yaml:3: secrets.detectors: detector set 3 doesn't exist; this build has sets 1 (the 12 built-in value patterns) and 2 (those, plus azure_storage_key, databricks_pat and sendgrid_api_key)
```

A pattern in `secrets.value_patterns` with the same name as a set-2 shape
replaces it. `secrets.enabled: false` turns set 2 off along with every other
detector. A set-2 finding is redacted like any other:
`matched "da…" (<redacted>, 36 chars)`. Two details of the count: an Azure
match starts at `AccountName=`, so it is redacted as `"Ac…"` and counts the
account name, and a SendGrid match includes the character after the key,
because a key can end in `-` or `_`.

## What it ignores

These exceptions apply to the name rule only. A literal that matches a shape
is always reported.

- Names that refer to a credential without holding one: `secret_name`,
  `token_url`, `credentials_path` (`secrets.exempt_key_patterns`).
- Placeholders such as `changeme`, `your-api-key-here` and `<token>`
  (`allow_values`, `placeholder_patterns`).
- References such as `${VAR}`, `{{ env_var('X') }}` and f-string
  substitutions. A template is judged by what it writes down, so a
  hardcoded fallback is still reported: `{{ env_var('X', 's3cr3t') }}`,
  `{{ 's3cr3t' }}`, or a `{% if %}` branch that is a literal.
- Values shorter than `min_value_length`.

Names are matched as written and in snake_case, so `privateKey` matches
`*private_key*`.

## How to fix it

Read the value from the environment or a secret store:

```python
import os
DB_PASSWORD = os.environ["DB_PASSWORD"]
```

`kv-cli fix` makes this rewrite and adds `import os` if it is missing. A
hardcoded default in a function signature is left as a `manual:` item,
because `os.environ[...]` in a default is read once, at import time.

Afterwards, rotate the credential. A value that was ever committed is still
in git history, whatever the file says now.

## How to suppress one line

```python
legacy_token = "abcd1234efgh"  # kovallent:allow-secret
```

The marker counts only inside a comment. JSON has no comments, so exclude a
fixture file with `scan.exclude` instead.
