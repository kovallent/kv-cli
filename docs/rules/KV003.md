# KV003: pinned infrastructure identifier

Severity: a warning by default, so turning it on doesn't break CI on day one.
Set `infrastructure.severity: error` to gate on it, or run `audit --strict`.

## What it catches

An identifier that ties code to one environment, such as a warehouse,
catalog, bucket, cluster ID, workspace URL, broker or JDBC endpoint. The
code works in that one environment and either breaks in the others or,
worse, writes to the wrong one.

```python
from snowflake.snowpark import Session

WAREHOUSE = "ANALYTICS_PROD_WH"           # KV003: name rule
df.write.parquet("s3://acme-prod-orders/") # KV003: object-store URI
```

Python files, [Databricks asset bundles](#databricks-asset-bundles) and
[dbt SQL models](#dbt-sql-models). Other config files, dbt's `profiles.yml`
above all, are where environment-specific values belong, so KV003 never
applies to them.

The name rule, `infrastructure.key_patterns`, applies only in files that use
a data framework, that is, where a framework profile is detected. In a file
that imports none, a `warehouse` or `bucket` is as likely to be a CLI option
or a test fixture as a deployment target. Value patterns, such as the
object-store URI above, apply in every Python file. To apply the name rule in
every Python file, as before 0.10.0, set
`infrastructure.global_key_patterns_require_framework: false`.

Framework profiles add their own identifiers in files that use the
framework. For example, Snowpark adds `account` and `role`, and Airflow adds
`conn_id`, `pool` and `queue`. `kv-cli frameworks` lists them all.

## Databricks asset bundles

A bundle declares what varies between targets, under `targets:` and
`variables:`, so an identifier anywhere else in it is pinned by mistake.
KV003 applies to `databricks.yml` (or `databricks.yaml`) and to the YAML
files its `include:` globs name, such as `resources/*.yml`. A file belongs to
the nearest `databricks.yml` above it, up to the repository root. dbt's
`profiles.yml` never counts, even when a bundle includes it.

```yaml
resources:
  jobs:
    nightly:
      tasks:
        - task_key: load
          existing_cluster_id: 0923-164208-prdclstr # KV003
          spark_python_task:
            parameters:
              - s3://prod-orders/raw/ # KV003
        - task_key: report
          sql_task:
            warehouse_id: ${var.warehouse_id} # a substitution: not reported

targets:
  dev:
    resources:
      jobs:
        nightly:
          tasks:
            - task_key: load
              existing_cluster_id: 0101-000000-devclstr # per target: not reported
```

A scalar is reported when all of these hold:

- it isn't under `targets:` or `variables:` (a variable's `default` is a
  declared default);
- it isn't a substitution such as `${var.x}`, `${bundle.target}`,
  `${workspace.host}` or `${resources.jobs.x.id}`;
- its key matches `infrastructure.key_patterns` or the databricks profile's
  infrastructure keys, such as `*warehouse_id*` and `*instance_pool*`, or its
  value matches `infrastructure.value_patterns`, such as an `s3://` URI.

`allow_values`, `exempt_key_patterns`, `min_value_length` and the
`kovallent:allow-infra` marker work as they do in Python. The finding's
`symbol` is the scalar's dotted path,
`resources.jobs.nightly.tasks[0].existing_cluster_id`, so its fingerprint
survives a moved line. A bundle file's entry in `run.files` reads
`analysis: credentials_and_infrastructure`.

Fix it by moving the value under `targets:`, or into a variable used as
`${var.<name>}`. Set `infrastructure.bundle_files: false` to make every YAML
file credentials-only again, as before 0.13.0.

## dbt SQL models

From 0.14.0, KV003 reads the `.sql` models of each dbt project in the scan.
A model is a `.sql` file under the `model-paths` (`source-paths` before dbt
1.0) or `snapshot-paths` of the nearest `dbt_project.yml` above it, up to the
repository root. `scan.include` doesn't need to list `.sql`. The project's
`target-path`, `dbt_packages/` and `dbt_modules/` are never read, and
`scan.exclude` still applies.

```sql
use warehouse ANALYTICS_PROD_WH;                          -- KV003: use_warehouse
select o.order_id
from ANALYTICS_PROD.RAW.ORDERS as o                       -- KV003: three_part_name
join {{ ref('stg_customers') }} as c on c.id = o.customer_id  -- a ref(): not reported
```

kv-cli doesn't render Jinja: it replaces each tag with text of the same
length, so lines stay exact, and parses the result with sqlparser-rs. A
`ref()` or `source()` becomes a placeholder and is never reported. These are
reported, each as its own `detector`:

| `detector` | What | `subject` |
| --- | --- | --- |
| `three_part_name` | A literal `database.schema.table` relation, in `FROM` or `JOIN`, or the target of `INSERT`, `MERGE`, `UPDATE` or `DELETE` | The name, unquoted and lower-cased: `analytics_prod.raw.orders` |
| `use_warehouse` | `USE WAREHOUSE x` | `x`, normalised |
| `use_database` | `USE DATABASE x` | `x`, normalised |
| `object_store_uri` | A string literal matching the `object_store_uri` value pattern, in a `COPY INTO … FROM` or `TO` clause, as the target of an unload (`COPY INTO '<uri>' FROM …`), or directly after `LOCATION` | The URI exactly as matched |
| `two_part_name` | A literal `schema.table` relation, only with `sql.two_part_names: true` | The name, normalised |

An unload writes to its target, so a hardcoded path there is reported like
one it reads from:

```sql
copy into 's3://acme-prod-exports/orders/'  -- KV003: object_store_uri
from {{ ref('orders') }}
```

Not reported:

- a name or string with Jinja in it, such as
  `analytics_{{ target.name }}.raw.orders` or `'s3://{{ var("bucket") }}/'`:
  it varies by target. A tag that is one quoted string,
  `{{ 'ANALYTICS_PROD.RAW.ORDERS' }}`, writes that string, so it is reported;
- CTE names and aliases, and a two-part name whose first part is one, such as
  BigQuery's `from orders o, o.items`;
- table functions, such as `generate_series(…)` or `read_files(…)`;
- names that `sql.allow_names` matches, ignoring case: by default anything
  with an `information_schema` part, `pg_catalog.*`,
  `snowflake.account_usage.*`, `snowflake.organization_usage.*` and
  `bigquery-public-data.*`;
- a value in `infrastructure.allow_values`, and a line whose comment carries
  `-- kovallent:allow-infra`.

The finding's `symbol` is the model name, its file stem, and its `subject` is
the pinned thing, so two hardcoded tables in one model are two findings with
their own fingerprints. The same thing written twice in one model is one
finding, at its first line, and its detail lists the others. `key` is the
name as written; it is absent for a URI.

A model that no SQL dialect parses, or whose Jinja can't be neutralised, is
listed in `skipped` as `sql_not_parsed`: a warning, which gates under
`--strict`, like a Python syntax error. Its detail names the cause. The same
rules still run over its tokens, and their findings say so. A model that
parses reads `analysis: sql` in `run.files`; SQL adds nothing to the scope
block's function counts.

Stage 1 doesn't check:

- names built or stored in Jinja, such as `{% set t = '…' %}` used as
  `{{ t }}`;
- hooks: `pre_hook`, `post_hook` and the hooks in `dbt_project.yml`;
- `config()` arguments, such as `snowflake_warehouse='PROD_WH'`;
- analyses and singular data tests;
- `USE SCHEMA`, `USE ROLE` and JDBC URLs;
- object-store paths outside `COPY` and `LOCATION`, such as
  `read_parquet('gs://…')`.

Fix a relation with `{{ ref() }}` or `{{ source() }}`, a `USE` statement by
setting the warehouse or database on the dbt target in `profiles.yml`, and a
path by passing it in with `var()` or `env_var()`. `kv-cli fix` lists each
SQL finding as a `manual:` item and never rewrites SQL. Set
`sql.enabled: false` to read no SQL, as before 0.14.0. See
[Configuration](../configuration.md#sql) for the `sql:` section.

## How to fix it

Derive the value from the target environment:

```python
WAREHOUSES = {"dev": "ANALYTICS_DEV_WH", "prod": "ANALYTICS_PROD_WH"}

def run_report(target_environment: str = "dev"):
    warehouse = WAREHOUSES[target_environment]
```

`kv-cli fix` never rewrites these, because the right replacement is a
deployment decision. In dbt SQL models it lists them as `manual:` items.

## What it ignores

- Values in `infrastructure.allow_values`, such as `local`, `dev` or `test`.
- Names in `infrastructure.exempt_key_patterns`, such as `*_column` or
  `*_type`.
- Values shorter than `min_value_length`.
- Comparisons such as `if catalog == "prod"`. Those branch on an environment
  rather than pin one.

## How to suppress one line

```python
LEGACY_BUCKET = "s3://acme-archive/"  # kovallent:allow-infra
```
